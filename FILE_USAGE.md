## File Summaries

### Form1.cs - Event Handler & UI Logic Layer
**Form1.cs** is the primary Windows Forms UI controller. It serves as the event-driven layer that handles user interactions, orchestrates file operations, and manages the user experience through real-time progress updates and error handling. It delegates actual cryptographic operations to specialized engines.

### Form1.Designer.cs - UI Layout & Component Definition
**Form1.Designer.cs** is the auto-generated UI designer file that defines all visual components and their properties. This file should **never be manually edited** (it's auto-generated by Visual Studio's Designer tool). It initializes all UI components, applies property configurations, and wires event handlers to Form1.cs methods.

### FileEncryptionEngine.cs - Cryptographic Encryption Module
**FileEncryptionEngine.cs** is a static utility class providing secure, streaming-based file encryption using **AES-256-GCM** (Galois/Counter Mode) with **PBKDF2** key derivation. It handles large files efficiently through chunked streaming, maintains cryptographic integrity with authentication tags, and provides high-security encryption resistant to tampering and password attacks.

### FileShredderEngine.cs - Secure File Deletion Module  
**FileShredderEngine.cs** is a static utility class implementing secure file destruction through multi-pass overwriting, disk cache flushing, metadata obfuscation, and final deletion. It prevents data recovery by overwriting file sectors with cryptographically random data and zeros across multiple passes, ensuring sensitive files cannot be recovered via forensic analysis.

## Cryptographic Architecture

### FileEncryptionEngine - Detailed Design

**File Format Structure:**
```
[Magic Header (4B)] [Salt (16B)] [Base Nonce (12B)] [Chunk 1...] [Chunk N...]

Each Chunk:
[Length (4B)] [Auth Tag (16B)] [Encrypted Payload (variable)]
```

**Key Components:**
- **Magic Header:** "SENC" (4 bytes) - File signature for validation
- **Salt:** 128-bit random value - Prevents rainbow table attacks
- **Base Nonce:** 96-bit random value - Base for chunk-specific nonces
- **PBKDF2 Iterations:** 600,000 - Password-based key derivation (SHA-256)
- **Key Size:** 256-bit AES key
- **Authentication Tag:** 128-bit GCM tag per chunk - Detects tampering
- **Chunk Size:** 64 KB - Balanced for memory and streaming efficiency
- **Nonce Derivation:** Base nonce XOR with chunk counter - Ensures unique IV per chunk

**Encryption Process:**
1. Generate cryptographically random salt and base nonce
2. Derive 256-bit AES key from password using PBKDF2 (SHA-256, 600K iterations)
3. Write file header: magic + salt + base nonce
4. For each 64 KB chunk:
   - Derive unique nonce by XORing base nonce with chunk index
   - Encrypt chunk with AES-256-GCM
   - Write: chunk length + authentication tag + ciphertext
5. Securely zero the key in memory

**Decryption Process:**
1. Validate file signature ("SENC")
2. Read salt and base nonce from header
3. Derive same AES key from password using PBKDF2
4. For each encrypted chunk:
   - Read chunk length, authentication tag, and ciphertext
   - Derive same chunk nonce
   - Decrypt and authenticate with AES-256-GCM
   - Verify authentication tag (prevents tampering)
   - Write plaintext to output file
5. Securely zero the key in memory
6. Cleanup partial file on authentication failure

### FileShredderEngine - Detailed Design

**Multi-Pass Overwriting Strategy:**
```
Pass 1: Cryptographically random data (fills all file sectors)
Pass 2: All zeros (0x00 bytes)
Pass 3: Cryptographically random data (final obfuscation)
```

**Secure Deletion Process:**
1. Remove file attributes (ReadOnly, System)
2. Open file in exclusive write mode
3. For each of 3 passes:
   - Overwrite entire file with pattern data
   - Flush OS buffers directly to disk (`FlushToDisk = true`)
4. Truncate file to 0 bytes
5. Rename to random filename (obfuscate directory entry)
6. Delete the file
7. Progress reporting: Combined across all passes (0-100%)

**Security Features:**
- **Cryptographic Randomness:** Uses `System.Security.Cryptography.RandomNumberGenerator`
- **Disk Cache Flushing:** `stream.Flush(flushToDisk: true)` forces writes to physical media
- **Metadata Obfuscation:** Random rename before deletion obfuscates file history
- **64 KB Buffer:** Efficient I/O for large files
- **Async Support:** Non-blocking file operations with cancellation support

## Application Execution Flow

### **Initialization**
1. Application loads Form1
2. `InitializeComponent()` (Designer.cs) creates all UI components
3. `SetupDropZoneEvents()` wires drag-and-drop event handlers
4. Application window displays and awaits user interaction

### **File Selection Workflow**
1. User drags file into `pnlDropZone`
2. `DropZone_DragEnter()` validates file (not text/data)
3. Visual feedback: blue highlight
4. `DropZone_DragDrop()` accepts file:
   - Stores file path in `_selectedFilePath`
   - Detects `.enc` extension (encrypted file?)
   - Updates `lblDropText` with filename
   - Enables encrypt/decrypt buttons
   - Auto-suggests action (encrypt or decrypt)

### **Encryption Workflow**
1. User enters password in `txtPassword`
2. Optionally checks `chkShred` to destroy original
3. Clicks `btnEncrypt`
4. Form1.cs: `btnEncrypt_Click()` initiates:
   - Validates file exists and password entered
   - Disables UI controls
   - Shows `prgProgress`
   - Calls **FileEncryptionEngine.EncryptFileAsync()**:
     - Generates random salt and base nonce
     - Derives AES-256 key via PBKDF2
     - Streams file through AES-256-GCM encryption
     - Writes `.enc` file with header and encrypted chunks
     - Reports progress (0-100%)
   - If `chkShred` checked: Calls **FileShredderEngine.ShredFileAsync()**:
     - 3-pass overwrite with random data and zeros
     - Flushes disk cache after each pass
     - Renames file to random name
     - Deletes original
   - Displays success message
   - Re-enables controls

### **Decryption Workflow**
1. User drags `.enc` file into drop zone
2. Automatically suggests decryption
3. User enters password (must match encryption password)
4. Clicks `btnDecrypt`
5. Form1.cs: `btnDecrypt_Click()` initiates:
   - Determines output filename (strips `.enc` or adds `.dec`)
   - Checks for file conflicts
   - Calls **FileEncryptionEngine.DecryptFileAsync()**:
     - Validates "SENC" magic header
     - Reads salt and base nonce
     - Derives AES-256 key using same password and salt
     - For each chunk:
       - Verifies authentication tag
       - Decrypts chunk via AES-256-GCM
       - Writes plaintext to output
       - Reports progress (0-100%)
     - On tag mismatch: Throws cryptographic exception
     - Cleans up partial file on failure
   - Displays success or error message
   - Re-enables controls

### **Error Handling**
- **Invalid File Format:** Rejects non-SENC files at header validation
- **Wrong Password:** Authentication tag mismatch detected during decryption
- **Corrupted File:** Tag verification fails, partial file cleaned up
- **File Locked:** IOException caught; user prompted to close file in other programs
- **Cancellation:** CancellationToken support allows user to abort long operations

## Security Considerations

### ✅ Cryptographic Strengths

**FileEncryptionEngine:**
- ✅ AES-256-GCM provides authenticated encryption (confidentiality + integrity)
- ✅ PBKDF2 with 600,000 iterations resists brute-force password attacks
- ✅ Unique nonce per chunk via XOR with counter prevents IV reuse
- ✅ 128-bit authentication tag detects any file tampering
- ✅ Cryptographic key securely zeroed in memory after use
- ✅ No hardcoded encryption parameters; all generated fresh per file
- ✅ Fixed-time comparison for header validation (timing-attack resistant)
- ✅ File signature prevents misidentification of non-encrypted files

**FileShredderEngine:**
- ✅ Multi-pass overwriting (3 passes: random → zeros → random)
- ✅ Cryptographically random data (not pseudorandom)
- ✅ Disk cache flushing forces writes to physical media
- ✅ Metadata obfuscation via random file renaming
- ✅ Async operations prevent UI freezing
- ✅ CancellationToken support allows operation abort
- ✅ No file data exposed in error messages

### ⚠️ Implementation Notes

**FileEncryptionEngine:**
- Password remains in memory during encryption/decryption (acceptable for UI layer)
- Large files (> available RAM) handled via streaming with 64 KB chunks
- Output file created even if encryption fails (cleanup is caller's responsibility)

**FileShredderEngine:**
- Shredding effectiveness depends on storage media type (SSD vs HDD)
- File system overwrites may be limited by FTL (Flash Translation Layer) on SSDs
- Network drives or encrypted filesystems may not honor flush-to-disk requests
- 3-pass method is sufficient for modern systems (NIST-approved alternative to Gutmann)

**Overall Application:**
- Password field masked via `UseSystemPasswordChar = true`
- No sensitive data logged or output to console
- Error messages sanitized (no password echo)
- Supports large files via asynchronous streaming
- Progress reporting doesn't expose plaintext content

## File Relationship Architecture

```
User Interface Layer:
  Form1.cs (UI Logic)
  Form1.Designer.cs (UI Layout)
           ↓ Calls
Cryptographic Layer:
  FileEncryptionEngine.cs (Encrypt/Decrypt)
  FileShredderEngine.cs (Secure Delete)
           ↓ Uses
System Layer:
  System.Security.Cryptography (AES-256-GCM, PBKDF2)
  System.IO (FileStream, File Operations)
  System.Windows.Forms (UI Components)
```

All crypto operations are isolated in static engines, making the code testable and maintainable while keeping sensitive operations separate from UI logic.
